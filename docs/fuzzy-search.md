# 跨方言模糊搜尋：演算法說明

實作在 `src/fuzzy/`（`babizu/fuzzy`，零依賴，瀏覽器與 Node.js 皆可用）與 `src/search/`（`babizu/search`）。
本文件說明數學定義、正確性論證、效能，以及日後可以怎麼擴充；API 摘要在最後一節。

文中的例子取自巴宰–噶哈巫語的語言設定檔（這個框架最初為它而寫），但演算法本身與語言無關：
規則、成本、正規化都來自各站台的語言設定檔（見 [language-profile.md](language-profile.md)）。
第 3、4 節也修正了常見說法中兩處在實作上不成立的地方。

## 1. 距離的定義

給定查詢字串 X（長度 N）與候選字串 Y（長度 M），兩者都已正規化並拆成 code point。D(i, j) 是把 X 的前 i 個字元轉成 Y 的前 j 個字元的最小成本：

```
D(0, 0) = 0
D(i, j) = min {
  D(i-1, j)       + del(X[i])              刪除（預設 1.0）
  D(i, j-1)       + ins(Y[j])              插入（預設 0.8）
  D(i-1, j-1)     + sub(X[i], Y[j])        替換（預設 1.5，相同字元 0）
  D(i-|s|, j-|t|) + w     對每條規則 s→t：   s 是 X 在 i 結尾的後綴、t 是 Y 在 j 結尾的後綴
}
```

- 空白的插入、刪除、替換成本是 0.1（`CostModel` 的字元覆寫）。
- 規則可以是多字元對多字元（`aru → aw`），`s` 或 `t` 其中一側可以是空字串（`r → ""` 表示 r 脫落），但不能兩側都空。
- 規則預設**自動補反向**（`r → ""` 同時註冊 `"" → r`），所以語音規則對查詢方向是對稱的；只有基本的刪除、插入成本不對稱。
- 所有成本非負，這是剪枝能成立的前提。建立規則與成本時會檢查。

### 正規化

正規化由語言設定檔的 `normalizer` 決定，依序：NFC → 轉小寫 → 逐字元對應（撇號統一、`ǝ`→`ə` 等，加上語言自己的對應）
→ 去除附加符號（保留指定字元，例如噶哈巫語的 `é`）→ 整理空白。

搜尋端（`src/search/text.js`）另外刪除辭典體例符號（`notationChars`，預設 `- = < > … ~ *`）。規則字串也會經過同一個正規化。

## 2. 位置限制

規則可以限定位置：

| position | 條件 |
|---|---|
| `any` | 無 |
| `initial` | `s` 位於 X 的詞首，且 `t` 位於 Y 的詞首 |
| `final` | `s` 位於 X 的詞尾，且 `t` 位於 Y 的詞尾 |

「詞首」指前一字元不存在或是邊界字元，「詞尾」指後一字元不存在或是邊界字元；邊界字元預設為空白。所以在片語中也適用：`bintul a ≈ bintun a` 距離 0.1。

## 3. 詞圖搜尋與「詞尾列」

在詞圖（DAWG，見第 9 節）上做深度優先走訪。深度 j 的節點代表 Y 的前 j 個字元已經確定，於是計算 DP 的第 j 列。共用前綴的詞共用上層的列。

**難點**：規則的 X 側位置條件在查詢時就能確定，Y 側的 `initial` 也只需往回看路徑；但 Y 側的 `final` 要看**下一個字元**，而同一個節點可能有多個子節點，下一個字元不唯一。原分析報告的做法是「到葉節點才重算 final 規則」，這不夠：

1. 詞尾不只出現在葉節點。片語中空白前面也是詞尾，而且這個值會被後面的列引用。
2. final 規則的結果必須參與同一列的後續轉移，例如同列刪除；只在結尾補算一次不正確。

**做法**：每個節點最多計算兩列。

- `N_j`：假設 Y[j+1] 存在且不是邊界，不允許 final 規則
- `F_j`：假設 Y[j+1] 不存在或是邊界，允許 final 規則

使用規則：

- 節點本身是詞尾時，距離取 `F_j[N]`。
- 後面的列引用第 r 列時，依路徑上實際的 Y[r+1] 選用 `F_r` 或 `N_r`，這在往下走時是已知的。
- `F_j` 只在「本節點是詞尾」或「有邊界字元的子節點」時才需要，所以大多數節點只算一列。

詞圖會合併共同後綴，同一個節點可能在走訪中出現在不同位置。這不影響正確性：
DP 的列取決於「走到這裡的路徑」，而深度優先走訪中每條路徑只會走一次。

實作見 `src/fuzzy/dp.js` 的 `fillRow(…, allowFinal, …)`。兩字串距離、`explain`、詞圖搜尋都呼叫這同一個函式，保證三者結果一致。

## 4. 剪枝的正確性

所有成本非負，所以沿任何轉移路徑，累積成本單調不減。

**原報告的說法是「當前列的最小值超過門檻就剪枝」，在有多字元規則時不成立**：像 `aru → aw` 這種 target 長度為 2 的規則，可以從第 j-1 列直接跳到第 j+1 列，越過第 j 列。第 j 列的最小值再大，也不代表子樹沒有答案。

**正確的下界**：令 L 為最長的規則 target 長度。任何通往第 j 列以下的路徑，最後一個「列 ≤ j」的格子一定落在第 j-L+1 … j 列之內，下一步離開到第 j 列以下。分兩種情況：

- 該格在第 j 列：下一步進入某個子節點 c，來源列是 `N_j`（c 非邊界）或 `F_j`（c 是邊界）。成本 ≥ 對應列的最小值。
- 該格在第 r 列（r < j）：下一步必須是一條 target 長度 > j-r 的規則，且 target 的前 j-r 個字元等於路徑上已確定的 `path[r..j)`。成本 ≥ min(第 r 列) + 這類規則的最小權重。

兩者取最小值即為整棵子樹的距離下界。下界大於允許上界時剪枝。

第二種情況的「這類規則的最小權重」是 target trie 上每個真前綴節點的 jump 值，由路徑匹配器逐層提供（第 6.2 節）。若不檢查前綴、把前 L 列一律納入，下界會太鬆：例如巴宰–噶哈巫語的規則有 `say → tshay`，L = 5，前 5 層幾乎無法剪枝。

**驗證**：`test/fuzzy/fuzzy-index.test.js` 的性質測試。

- 隨機產生規則（含多字元、空字串、詞首詞尾、單向）、隨機詞庫（含空白）、隨機門檻與正規化策略。
- 檢查詞圖搜尋結果與「對每個詞暴力計算距離」完全相同。
- 實作時故意改成「只看當前列」「不區分 N／F」「子節點是邊界時用 N_j」三種錯誤版本，這個測試都會失敗。

## 5. 正規化距離與剪枝

依長度正規化，例如 d / max(|X|, |Y|)，**不滿足三角不等式**（Marzal & Vidal 1993）。這也是不使用 BK-tree、VP-tree 這類度量樹的原因：它們的剪枝依賴三角不等式，會漏掉結果。SymSpell 只處理對稱刪除，無法表達加權的多字元規則。

正規化門檻在詞圖上的處理：每個節點記錄 `height`（子樹中最長詞比本節點多幾個字元）。子樹內候選字串長度 ≤ j + height，把正規化門檻 t 換算成絕對距離上界：

| 策略 | 分數 | 子樹的絕對距離上界 |
|---|---|---|
| `max` | d / max(N, M) | t · max(N, j + height) |
| `sum` | 2d / (N + M) | t · (N + j + height) / 2 |
| `query` | d / N | t · N |

上界對 M 單調不減，所以用子樹最長詞計算出的上界對整棵子樹都成立。正規化分數只在抵達詞尾時計算。

## 6. 規則索引與「每格只剩陣列存取」的實作

遞推式（第 1 節）決定了要算什麼；這一節說明怎麼讓每一格的計算只剩陣列讀取與加法。實作在 `src/fuzzy/dp.js`，檔頭有逐項說明。

### 6.1 三張表

1. **字元編號**：每個字元給一個小整數（`CompiledRules.idOf`）。規則 target 中的字元最先編號，其他字元（詞庫、查詢）第一次用到時才編號。詞圖每條邊的編號在第一次搜尋時算好並快取（`FuzzyIndex._edgeCodes`）。
2. **查詢端的成本表**（`compileQuery`，每個查詢一次）：
   - `del[i]` = del(X[i-1])
   - 對每個候選字元 y 的替換成本列 sub(X[i-1], y)：y 第一次出現時才算，之後共用
   - ins(y)
3. **查詢端的規則表**：source 恰好結束在 X 的位置 i、且 X 側位置條件成立的規則，依 **target 編號**分組，存成平坦陣列（位置、source 長度、權重、initial／final 旗標）。

### 6.2 target trie 與路徑匹配器

計算第 j 列時，要知道「哪些規則的 target 恰好是 Y 在位置 j 結尾的後綴」。所有 target 建成一棵 trie，沿著詞圖路徑逐層維護「可能還在某個 target 中間」的 trie 狀態集合（`PathMatcher`）：

```
states(j) = { child(s, Y[j-1]) : s ∈ states(j-1) ∪ {root} }
```

這就是 Aho–Corasick 自動機的「所有部分匹配」。規則少、target 短（≤ 5），所以直接保留整個集合（每層最多 5 個狀態），比建失敗連結簡單。同一組狀態提供兩種資訊：

- **狀態是某個 target 的結尾**：這個 target 以長度 t = depth(s) 結束在 j，對應規則的來源列是第 j − t 列。
- **狀態還能延伸成更長的 target**：第 r = j − depth(s) 列可以經由更長的規則跳過第 j 列。第 4 節的剪枝下界要加入 min(第 r 列) + jump(s)，其中 jump(s) 是經過 s 的更長 target 的最小權重。

狀態只依賴路徑，與查詢無關，所以多通道搜尋（第 10 節）中每個詞圖節點只算一次，所有通道共用。

### 6.3 計算一列

`fillRow` 對每個匹配到的 target，先把它的規則轉移整批算進暫存列 `ruleMin`：這些轉移只讀較早的列，與本列的順序無關。主迴圈每格只做插入、替換、刪除三個加法，再比一次 `ruleMin[i]`。
- target 為空字串的脫落規則，來源是同一列較小的 i，所以在主迴圈中依 i 的順序處理。
- 列的最小值在迴圈中順便算出，剪枝不必再掃一次。

**每一格的候選值仍以同一對浮點數相加得到，取 min 又與順序無關，所以結果與舊的實作逐位元相同**（驗證方法見第 12 節）。追蹤模式（explain、演算法實驗室）走另一條較慢的分支，逐一回報候選轉移，回報順序也與舊的實作相同。

### 6.4 舊的做法（commit e1557f4 之前）與它慢在哪裡

舊的做法是：每個查詢建立 `at[i]`，也就是以 target 字串為鍵的 Map；每個詞圖節點把 Y 的各長度後綴串成字串，每一格再拿這些字串查 `at[i]`；替換、刪除成本則每格以字元查覆寫表（`Map<string>`）。

CPU 剖析顯示，時間的 43% 花在 `fillRow`，而其中大部分是這些字串雜湊查詢，每格約 230 ns。改成上面的表之後，同一批查詢的構詞搜尋快約 4 倍，普通搜尋快約 3.4 倍（第 12 節）。

## 7. 複雜度與實測

記 L 為最長的 target 長度（巴宰–噶哈巫語為 5），k 為本列匹配到的 target 在 X 中的規則數。
- **每個詞圖節點**：路徑匹配器推進一層，O(L)；所有通道共用。
- **每一列**：O(N + k)。主迴圈每格三個加法、一次比較；規則轉移整批算進暫存列。
- **兩字串距離**：O(N · M + Σk)；**詞圖搜尋**：O(V · (L + N) + Σk)，V 是走訪的節點數，由剪枝決定。

舊的做法（第 6.4 節）每格要做 O(T) 次字串雜湊查詢（T 是不同 target 長度的個數，本語言為 5），外加兩到三次覆寫表查詢；漸近複雜度相同，常數差很多。

實測一：`npm run bench`（2 萬個假詞、18,622 個節點，巴宰–噶哈巫語的規則；同一台機器，舊、新交錯各跑兩次，取第二次）。走訪節點數與結果數兩者完全相同：

| 門檻 | 舊的實作（平均／p95） | 目前（平均／p95） | 平均走訪節點 |
|---|---|---|---|
| maxDistance 0.3 | 1.67／3.04 ms | 0.60／1.11 ms | 1,095 |
| maxDistance 1 | 7.10／11.04 ms | 1.94／2.83 ms | 5,143 |
| maxDistance 1.5 | 8.39／13.86 ms | 2.28／3.60 ms | 5,952 |

實測二：巴宰–噶哈巫語數位辭典的搜尋引擎（600 個真實詞，新舊兩版在同一個行程逐查詢交錯執行，中位數／p95）：

| | 舊的實作 | 目前 | 加速 |
|---|---|---|---|
| 標準，不含構詞 | 6.34／23.65 ms | 1.82／6.96 ms | 3.5× |
| 寬鬆，不含構詞 | 24.47／83.34 ms | 7.21／21.04 ms | 3.4× |
| 標準，含構詞 | 12.87／60.73 ms | 4.24／28.12 ms | 3.0× |
| 寬鬆，含構詞 | 29.82／119.83 ms | 9.26／40.66 ms | 3.2× |

含構詞時 p95 仍偏高，來源不是詞圖搜尋，而是多詞片語中的短詞（例如 `ma`）觸發的「衍生形」查詢：對每個含有該詞的詞重跑列舉式構詞分析（見第 10.7 節）。

## 8. 短查詢與前綴：為什麼還需要另一套索引

加權編輯距離只適合「長度相近、拼寫相近」的兩個詞。實際使用時有兩種需求它天生做不到：

| 使用者輸入 | 期待 | 加權編輯距離的結果 |
|---|---|---|
| `pihi`（只記得詞的開頭） | 找到 `pihilut`「尿」 | 要插入 `lut` 三個字元 ≈ 2.4，遠超過門檻 |
| `k`（想看看哪些詞、句子含有 k） | 列出所有含 k 的詞與句子 | 單一字母與任何詞的距離都很大；正規化門檻也會把長詞全部排除 |

把門檻調高並不能解決：距離門檻一旦放大到 2.4，`bintul` 也會配到幾百個無關的詞，
而且短查詢在「除以較長字串長度」的正規化下永遠吃虧。這是度量本身的性質，不是參數問題。

### 解法：兩種索引各做自己擅長的事

保持加權編輯距離**不變**（它負責跨方言、跨拼寫的相似比對），另外加一個**字元 → 詞**的反向索引，
負責前綴與包含比對。兩者的結果合併後再排序。

```
查詢 → ┬─ 詞圖 + 加權編輯距離 ──→ 模糊命中（含距離與規則說明）
       └─ 字元反向索引 ─────────→ 前綴命中、包含命中
                                    ↓
                        合併、去重，依「模糊 → 前綴 → 包含」分組排序
```

實作在 `src/search/engine.js` 的 `_matchTerms()`：

1. `_fuzzyTerms()`：原本的詞圖搜尋。
2. `_substringTerms()`：取查詢字串中**出現次數最少**的字元，拿它的 posting 當候選集，
   再逐一用 `includes()` 驗證，並分成「以查詢開頭（prefix）」與「包含查詢（substring）」兩類。
   兩類各自依詞長排序（越短代表多出來的部分越少），合計最多取 300 個詞。
3. 兩邊的結果以詞為鍵合併；同一個詞若兩邊都命中，以模糊命中為準（有距離資訊可以顯示規則）。

之後的流程完全共用：詞的 posting 指出它是哪些記錄的詞形、變體、詞根，或出現在哪些句子中，
所以前綴與包含命中同樣會分別出現在「詞條」與「例句」兩區。

### 排序與標示

三種命中方式換算成同一個「等效距離」一起排序（`rankScore()`）：

| 命中方式 | 等效距離 |
|---|---|
| 模糊 | 加權編輯距離本身（完全相同 0、跨方言變體 0.1–0.3） |
| 前綴 | 0.35 ＋ 多出來的字元數 × 0.05 |
| 包含 | 0.90 ＋ 多出來的字元數 × 0.05 |

這組數字讓三種命中互相穿插得合理：

- `bintul`：精確命中（0）與跨方言的 `bintun`（0.1）仍在最前面，前綴命中 `bintulan`（0.45）其次。
- `pihi`：前綴命中 `pihilut`（0.50）排在「拼寫接近但距離較大」的 `pihik-`（0.80）之前——
  使用者打前四個字母時，想找的通常是那個以它開頭的詞。

每一筆結果都標示命中方式（介面上顯示「開頭相符」「包含」），使用者知道自己為什麼會看到這一筆。

### 成本

- 記憶體：字元 → 詞的反向索引，1.2 萬個詞約 8 萬筆 posting，載入後建立約 10 ms。
- 查詢：候選集是「最少見字元」的 posting。最壞情況是查單一常見字母（例如 `a`），
  候選約 8,000 個詞，驗證一次約 1–2 ms；實際查詢在實際辭典上約 2–20 ms。
- 結果量：單字母查詢會命中數百個詞、上千個句子，因此有 300 個詞的上限，
  介面也分頁顯示，並在總數上標明截斷。

### 為什麼不用其他方案

| 方案 | 不採用的原因 |
|---|---|
| 把 maxDistance 調大 | 短查詢會配到大量無關長詞，精確查詢的品質一起崩掉 |
| 在詞圖上做前綴走訪 | 只能解決前綴，解決不了「包含」；而且詞圖已被模糊搜尋使用，混在一起會讓剪枝邏輯難以維護 |
| n-gram 索引（2-gram、3-gram） | 空間大得多，且單一字母查詢仍需另外處理；字元索引 + 驗證已經夠快 |
| 後綴陣列／後綴自動機 | 能做到 O(查詢長度) 的包含比對，但建置與序列化複雜度高出許多，對 1.2 萬個詞的規模不划算 |

## 9. 資料結構：DAWG（`src/fuzzy/dawg.js`）

詞庫用 **DAWG**（有向無環詞圖，即最小化無環有限狀態自動機 MA-FSA）儲存。
Trie 只合併共同前綴，DAWG 進一步合併共同後綴——多數語言都有大量共同詞尾（巴宰–噶哈巫語的 -an、-en、-ay、-ən…），
合併後節點數大幅下降。

### 建構

採 Daciuk et al. (2000) 的漸進式最小化：詞依 code point 字典序加入，每加入一個詞就把
「上一個詞不再需要的尾段」最小化——若登記表中已有等價狀態（詞尾旗標與所有出邊都相同）就直接共用。
因為子節點一定比父節點先登記，節點編號天然是拓撲序（子 < 父），之後計算子樹資訊只要依編號掃一遍。

### 附帶資料：完美雜湊

節點會被多個詞共用，所以 payload 不能掛在節點上。每條邊記錄「這條邊之前有幾個詞」，
沿著詞走一遍把這些數字加起來就得到該詞的字典序名次，用名次索引 payload 陣列。
搜尋時的 DFS 順手累加同一個數字，抵達詞尾時即可取得 payload，沒有額外成本。

### 實測（12,319 個詞的實際詞庫）

| | Trie（Map 版） | DAWG（TypedArray） |
|---|---|---|
| 節點數 | 43,550 | 14,459（另有 24,051 條邊） |
| 記憶體 | 9.81 MB | **0.25 MB** |
| 序列化（gzip） | 約 122 KB | 約 152 KB |
| 查詢速度 | — | 相同（走訪的路徑數不變） |

記憶體差距這麼大，是因為 Map 版 Trie 每個節點都是一個 JS 物件加一個 Map；
DAWG 則是幾個 TypedArray（CSR 格式的 `edgeStart`／`edgeTarget`、邊標籤、詞尾旗標）。

**代價是序列化檔案略大**：樹可以用先序走訪隱含表示、完全不存指標，圖則必須明確存下每條邊的目標。
已用兩個編碼手段把差距壓到最小（以 gzip 後計）：
- 存每個節點的**出邊數**而非 CSR 絕對起點：34 KB → 4 KB
- 目標存「本節點編號 − 目標編號」：子節點一定比父節點早登記，差值中位數只有 7；47 KB → 30 KB

下載多出的約 30 KB，換到執行期少用約 9.5 MB 記憶體，對行動裝置是划算的。
子字串比對需要的詞表陣列（0.44 MB）只有在真的用到時才展開。

### 未來設計

2. **Double-Array DAWG**：把圖壓進兩個陣列（BASE／CHECK），可直接 mmap，載入時間接近零。
   `FuzzyIndex` 只依賴「列出出邊、是否為詞尾、height、詞數前綴和」四個操作，換底層時介面不變。

## 10. 構詞：音變 ∘ 構詞 ∘ 詞庫的聯合搜尋

語言設定檔有 `morphology`（見 [language-profile.md](language-profile.md#morphology-構詞選填)）時，搜尋會多兩種命中：

- **詞根相符**（`lemma`）：查衍生詞，找到詞根。例如 `minudox` → `daux-`：`minu-` ＋ `dox`，其中 dox → daux 是 o→au 的方言音變。
- **衍生形**（`derived`）：查詞根，找到詞庫與例句中由它衍生的詞，包括中綴形式。

「詞根相符」使用的演算法稱為 **BCDP（Boundary-Coupled DP，邊界耦合 DP）**：詞綴的成本圖表透過邊界條件（第 0 列與詞尾成本）耦合進詞圖上的編輯距離 DP。完整的設計文件見 [bcdp.md](bcdp.md)。

完整的研究紀錄（實驗設計、數據、證明）在私有 repo 的 `docs/research/morphology-search.md`；以下是精簡版。

### 10.1 問題與記號

- 查詢 q = x₁…xₙ；詞庫詞 t；E(u, v) 是本文件第 1 節的加權編輯距離（含方言規則）。
- 前綴清單 Pre、後綴清單 Suf 中每個詞綴 a 有成本 c_a（預設 0.3）。
- 要求的是「前綴鏈 · 帶音變的詞幹 · 後綴鏈」的最小總成本：

```
W(q, t) = min over 0 ≤ i < k ≤ n of  P[i] + E(q[i..k), t) + S[k]
```

- P[i]：把 q[0..i) 切成至多 maxSteps 個前綴的最小成本；每段與詞綴的距離可到 `affixDistance`（δ），所以詞綴本身的方言差異（`mine-`／`minu-`）也涵蓋在內。
- S[k]：q[k..n) 切成後綴鏈的最小成本。

### 10.2 做法：構詞圖表當作 DP 的邊界條件

1. **詞綴圖表**：P 由左而右、S 由右而左，以 Viterbi 填表。
   - 每個起點在前綴或後綴的 trie 上跑一次小型 DP；詞尾回呼會給出整列，也就是 q[k..k+l) 對每個詞綴的距離。
   - 依相依方向填表的想法來自 pika parser（Hutchison 2020）。
2. **邊界條件**：`dp.js` 的第 0 列改成 D(i, 0) = min(P[i], D(i−1, 0) + del(xᵢ))，詞尾取 min_k D(k, |t|) + S[k]。
   - 遞推式、方言規則、剪枝都不變。
   - 普通搜尋是 P = [0, ∞…]、S = [∞…, 0] 的特例。
   - 前綴鏈的終點也算詞首、後綴鏈的起點也算詞尾，詞首、詞尾規則才能套在詞幹上。
3. **兩階段求值**（`morph-search.js`）：
   - **候選**：邊界向量只保留「可以在這裡開始／結束」（有限值一律當 0），以 λ = `lemmaDistance` 為上限走訪詞圖。
     由定理 1，這一步找到的正是「存在 (i, k) 使 E(q[i..k), t) ≤ λ」的詞。詞幹音變的上限本來就是 λ，所以這是必要條件，一個也不漏；λ 小，剪枝緊。
   - **計價**：只對候選在有限的 (i, k) 組合上算真正的 P[i] + E + S[k]。
4. **非串接的構詞**（中綴、Ca 重疊、詞幹交替）：在前綴鏈終點拿掉中綴或重疊、在後綴鏈起點還原交替，得到少數還原變體，每個變體帶著自己的邊界向量。
5. **多通道走訪**（`FuzzyIndex.searchChannels`）：普通模糊搜尋與所有還原變體共用一次詞圖走訪。
   - 每個通道有自己的列與剪枝，某個通道剪掉只是它不再往下算。
   - 所以結果與分開搜尋相同，但走訪只做一次。

### 10.3 正確性

**定理 1（邊界條件）**：D′(k, j) = min over i ≤ k of ( start[i] + E(q[i..k), t[1..j]) )。

*證明*：對 (j, k) 的字典序歸納。
- j = 0：第 0 列只有起點與刪除，D′(k, 0) = min_i (start[i] + Σ del)。
- j ≥ 1：每個轉移把某格延長一個編輯操作，且在 (min, +) 中加法對 min 分配，(min_i aᵢ) + c = min_i (aᵢ + c)。
- 所以 min 可以提到最外層，其餘就是原 DP 的正確性。∎

**推論**：min_k D′(k, |t|) + end[k] = W(q, t)。

**定理 2（剪枝）**：第 3–4 節的下界只依賴「所有轉移成本非負」與「多字元規則的跳躍」。
start 只影響第 0 列，end ≥ 0 只加在詞尾，所以下界照樣成立。∎

**定理 3（圖表）**：P[i] 是位置圖 0…n 上（邊 k→i 的權重 c_a + E(q[k..i), a)）的最短路徑。
圖無環、權重非負，依位置順序鬆弛即得最佳解。∎

**實證**（`test/fuzzy/boundary.test.js`、`test/fuzzy/morph-search.test.js`）：以隨機規則、詞庫、邊界向量、詞綴清單，與暴力窮舉逐筆比對，結果完全相同。

**與 FST 聯合最佳解 W* 的關係**：W* 是把音變 E、構詞 M、詞庫 L 組合成 WFST 後的最短路徑（`babizu/fst` 的參考後端直接求它，並與暴力窮舉逐筆相同，見 `test/fst/fst.test.js`）。BCDP 求得的成本記為 W_D。兩者**互有高低**，不是單純的上下界：

- **BCDP 較高或找不到**：
  - BCDP 把詞綴段與詞幹段的編輯分開算，跨越切點的多字元規則無法當作一條規則使用。
  - 詞幹與詞綴的音變另有 λ、δ 上限。
  - 中綴、重疊要與查詢完全相同。
- **BCDP 較低或只有 BCDP 找到**：兩者的語意不同。
  - BCDP 把詞素交界也當作詞首、詞尾，詞尾的方言音變可以發生在後綴之前（例如 babulay 找到 babun）。這是巴宰–噶哈巫語的語言事實。
  - 重疊部分複製的是查詢（方言）的形式。

在 1,245 個評估查詢的全部 8,867 組命中上：
- 兩者相同 6,437 組；BCDP 較高 149 組、較低 26 組。
- 只有 BCDP 在上限內 269 組；只有 W* 在上限內 1,986 組。
- 只看標註詞根時，W_D 比 W* 高的佔 0.2–1.7%（差一條規則），沒有較低的。

完整的定義與分析見 [bcdp.md](bcdp.md)。

### 10.4 形式化觀點：分開定義、聯合求值

把詞庫 L、構詞 M（詞幹 → 表面詞形）、音變 E（查詢拼寫 → 標準拼寫）都看成 (min, +) 上的加權關係。

**組合**：
- 「查衍生詞找詞根」是 q ∘ E ∘ M⁻¹ ∘ L 的最短路徑。
- 組合 (R ∘ S)(x, z) = min_y R(x, y) + S(y, z) 滿足結合律（只用到 semiring 公理）。
- 加權有理關係在組合下封閉（Mohri 2009）。

所以 E 與 M 可以分開維護（規則由人寫、詞綴由資料學出），搜尋時再組合。

**逆轉**：交換輸入、輸出帶即得逆關係，「查詞根找衍生形」就是反向使用 M。限制有三：
- 是關係而不是函數（歧義）。
- 插入 0.8、刪除 1.0 不對稱。
- **完整重疊 {ww} 不是正規語言**（抽水引理），不能放進有限狀態組合。Ca 重疊是 ⋃_c c·a·c·Σ*，是有限狀態的。

**兩段式為什麼不夠**：先精確去詞綴再音變，或先音變再去詞綴，等於在聯合最佳化中加上「中間結果必須屬於某個集合」的限制，所以 W_串接 ≥ W*。
音變落在詞綴或跨越邊界時，第一段就已經丟掉了正確答案。

**與 FST 的比較**（完整的實驗設計、資料與分析在私有 repo 的研究紀錄 U.5–U.6）：

1. **通用 WFST 以成熟函式庫實作並不慢**。`babizu/fst` 的參考實作要 119 ms，但 rustfst 1.3.1 以同一個演算法（`compose` ＋ 惰性 `ComposeFst` ＋ 有界 Dijkstra）在瀏覽器（WASM）只要 3.8 ms；差距完全來自參考實作的寫法。
2. **兩邊用同等水準的資料結構比較**（整數字元、typed array，沒有字串雜湊；1,245 個構詞查詢，中位數／p95）：

   | 做法 | 求的是 | 耗時 |
   |---|---|---|
   | BCDP（本節，JS） | W_D（分段模型，見 10.3） | 1.31／3.51 ms |
   | 最佳優先的乘積搜尋（hfst-ospell 式，JS，ε 排序過濾） | W* | 1.87／3.51 ms |
   | 同上，rustfst 原生／WASM | W* | 1.20／2.30、1.70／3.26 ms |

3. **兩者的差異在哪裡**（量測，不是推論）：
   - 工作量相近：BCDP 的 DP 格子數中位數 24,003，最佳優先的鬆弛次數 19,650。
   - 每單位成本不同：DP 每格約 55 ns（連續的列、陣列存取、沒有對數因子）；最佳優先每次鬆弛約 95 ns（雜湊表與堆積）。
   - 查詢越長，BCDP 的格子數約隨查詢長度線性增加（≤ 6 字元 12,866 → ≥ 13 字元 69,225），最佳優先只從 15,169 增加到 31,036。長查詢（≥ 13 字元）時兩者耗時相當，最佳優先的 p95 較低。
   - 上限提高時，BCDP 的耗時不變（詞幹音變另受 λ 限制，走訪只依賴 λ），最佳優先則快速增加（上限 1.0／1.3／1.6：1.84／5.44／12.47 ms）。這反映兩者解的問題不同：W* 允許任意大的詞幹音變。
   - 普通模糊搜尋（兩者解同一個問題，結果逐詞相同）：標準門檻時相當（1.38 對 1.57 ms）；寬鬆門檻時詞圖 DP 快 4.6 倍（6.24 對 28.44 ms）。門檻大時幾乎整列都在上限內，最佳優先的「稀疏」優勢消失，只剩雜湊與堆積的額外成本。
4. **結論**：在本資料與網站的上限下，BCDP 較快；最佳優先搜尋的優點是精確（W*）與長查詢的擴展性。BCDP 保留為正式實作，最佳優先搜尋作為 W* 的參考與交叉驗證。

### 10.6 與完整 FST（lexc／twolc）的比較

| 面向 | 本方法 | 完整 FST |
|---|---|---|
| 工程難度 | 中：沿用詞圖 DP，只換起點與終點 | 高：通用組合、ε 過濾，另需撰寫構詞語法 |
| 維護 | JSON 規格，可由資料學出、可以過寬（只收詞庫中的詞幹） | 專用語法，需要 FST 專業 |
| 最佳成本 | 分段模型下的 W_D；與 W* 語意不同、互有高低（10.3） | FST 語意下精確的 W* |
| 表達力 | 詞綴槽位、中綴、Ca 重疊、交替；規則只有詞首／詞尾條件 | 任意有限狀態構詞與左右文；完整重疊需 compile-replace |
| 網站部署 | 純 JS，索引不變 | 最佳優先搜尋可用純 JS；rustfst 的 WASM 為 83 KB（gzip）。L 可在瀏覽器由詞庫與構詞規格建立 |
| 效能（10.5，構詞搜尋中位數） | 1.31 ms | 最佳優先的乘積搜尋：純 JS 1.87 ms、WASM 1.70 ms；上限提高時增加較快 |

### 10.7 之後可以做的

- **未知成分**（pika parser 的錯誤復原）：以間隙成本略過未收錄的詞綴或複合詞前半。原型在本資料上沒有增益，需要另設預算再評估。
- **輸入時的增量搜尋**：查詢只在尾端加字時，DP 只多一欄，可以快取各節點的列。
- **由資料估計詞綴成本**：c_a = −log P(a)，取代一律 0.3，改善第 1 名的比例（目前 65–77%）。
- **規則的左右文條件**（例如「只在 -an 之前」）：轉移時多一個條件判斷，成本仍非負，定理 2 不受影響。
- **衍生形方向的效能**：搜尋引擎的 `_derivedTerms` 對每個含有查詢詞核心形式的詞，都重跑一次列舉式構詞分析。
  - 多詞片語中的短詞（例如 `ma`）會對到很多詞，是目前含構詞搜尋 p95 的主要來源：在最慢的 40 個查詢中佔 53% 的時間。
  - 每個詞的分析與查詢無關，可以依詞快取，或在建置時建成「詞幹 → 衍生詞」的索引。
- **編譯查詢的成本**：`compileQuery` 以字串切片比對規則的 source，在構詞計價中佔約 8%。可以比照 target 改用 source 的 trie。

`search(query, { expanders })` 的查詢展開器（`src/fuzzy/expanders.js`）是較早的擴充點，仍然保留，但搜尋引擎改用 `morphology`。

## 11. API 摘要

```js
import { createMetricFromProfile, FuzzyIndex, RuleSet, WeightedEditDistance } from 'babizu/fuzzy'

const metric = createMetricFromProfile(profile) // 或 new WeightedEditDistance({ costs, rules, normalize, boundaries })
metric.distance('semer', 'semee') // 0.1
metric.normalizedDistance('semer', 'semee', 'max') // 0.02
metric.explain('semer', 'semee') // { distance, normalized, matrix, candidates, path, alignment, … }

const index = new FuzzyIndex(metric)
index.add('bintun', { id: 'pazih-dict:p087-03' }) // 第二個參數是任意附帶資料
index.search('bintul', { maxDistance: 1 }) // → [{ term: 'bintun', distance: 0.1, score: 0.1, payloads: […] }]
index.searchWithStats('bintul', { maxDistance: 1 }) // 另外回傳 visitedNodes、prunedNodes、computedRows
const data = index.serialize() // FuzzyIndex.deserialize(data, metric)
```

| 類別／函式 | 說明 |
|---|---|
| `WeightedEditDistance` | `distance`、`normalizedDistance(q, c, 'max' \| 'sum' \| 'query')`、`explain`、`setRules`、`setCosts`（正規化函式不可替換）；同一個查詢對很多候選字串時：`prepareQuery(prepare(q))` 一次，再 `distancePrepared(plan, prepare(c))` |
| `RuleSet` | `add(source, target, weight, { position, bidirectional, category })`、`RuleSet.fromTable(groups)`、`enable`／`disable(category)`、`categories()` |
| `CostModel` | 基本成本與單一字元覆寫 |
| `FuzzyIndex` | `add`、`addAll`、`lookup`、`search`、`searchWithStats`、`freeze`、`terms`、`payloads`、`dawg`、`serialize`／`deserialize` |
| `createNormalizer(options)` | 建立正規化函式；`DEFAULT_CHAR_MAP` 是預設字元對應 |
| `createMetricFromProfile`、`createRulesFromProfile`、`validateProfile` | 由語言設定檔建立 |
| `createAnalyzer(spec, normalize)` | 構詞分析器：`analyze`（去詞綴）、`generate`（還原詞綴）、`coreForms` |
| `createMorphSearch({ analyzer, metric, index })` | 構詞搜尋（10.2 節）：`search`、`prepare`／`finish`（搭配多通道走訪）、`charts` |
| `FuzzyIndex.searchChannels(channels)` | 多通道走訪；每個通道可帶 `start`／`end` 邊界向量與 `onTerminal` 回呼 |
| `babizu/fst`（實驗性） | 通用 WFST：`compose`、`shortestDistance`、`editTransducer`、`surfaceLexicon`、`fstLemmaSearch` |

搜尋引擎（`babizu/search`）在此之上處理記錄、斷詞、釋義搜尋與結果排序：

```js
const { docs, lexicon } = buildSearchIndex({ items, groups, sourceIds, profile, varieties }) // 建置端
const engine = new SearchEngine({ docs, lexicon, profile }) // 瀏覽器（Web Worker）
engine.search('bintul', { fuzziness: 'normal', filters: { dialects: ['pazeh'] } })
```

## 12. 效能工程：剖析、最佳化與驗證

第 6 節的實作改寫是依照下面的流程做的；日後再改動 DP 核心時，也應該照這個流程。

1. **先量測工作量與每單位成本，再下結論**。只比總時間，無法區分「演算法做了較多的工作」與「每單位工作較貴」。
   - 工作量：DP 的格子數、最佳優先的鬆弛次數、走訪節點數（`searchWithStats`）。
   - 每單位成本：總時間 ÷ 工作量。
   - CPU 剖析：`node --cpu-prof`，依函式的自身時間排序。

   舊的實作中，每格約 230 ns，其中 `fillRow` 佔 43%，大多是字串雜湊查詢。構詞計價重做正規化與編譯，約佔 20%。
2. **只改「怎麼找到候選值」，不改算式**。每一格的候選值仍是同一對浮點數相加，取 min 與順序無關，所以結果可以要求逐位元相同，不必重新驗證正確性。
3. **逐位元快照驗證**。改動前後對同一份資料各產生一次快照，每一項取 SHA-1 比對，涵蓋：
   - 搜尋引擎三種模糊程度（含與不含構詞，共 1,845 個查詢）
   - 構詞搜尋的命中與步驟
   - 詞圖走訪事件（演算法實驗室的 `onNode`）
   - 邊界條件與 `onTerminal` 的整列數值
   - `explain` 的整張 DP 表與候選轉移，以及 `distance`

   共 10,617 項。先確認快照本身可重現（搜尋回應中的耗時欄位要排除），再比對改動前後。本次改動 10,617 項全部相同，單元測試 193 項通過。
4. **A/B 量測**。把改動前的原始碼另存一份，與改動後的版本在同一個行程中逐查詢交錯執行，每個查詢各跑 5 輪取中位數，奇數查詢交換先後順序。同一台機器不同時間的量測可以相差 30% 以上，只有交錯執行的比值可信。

結果：構詞搜尋 BCDP 快 3.96 倍（走訪 4.05 倍、計價 3.41 倍），普通搜尋快 3.4–3.5 倍（第 7 節）。量測腳本與完整數據在私有 repo 的研究紀錄 U.6。
