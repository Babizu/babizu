# 語言設定檔

語言設定檔描述「搜尋時怎麼看待這個語言的拼寫」：哪些字元視為相同、哪些符號忽略、方言之間有哪些系統性的語音對應，以及（選填）這個語言的詞綴與構詞。
它是純資料（JSON），建置端用它建索引，網站的 Web Worker 用它處理查詢。兩邊讀同一份檔案，搜尋鍵才會一致。

這份文件前半說明每個欄位，後半（[編寫指南](#編寫指南)）說明怎麼為一個新的語言寫出方言規則與構詞規格、怎麼檢查、常見的錯誤。

## 完整範例

```json
{
  "format": "babizu-language-profile",
  "version": 1,
  "name": { "zh-TW": "示範語", "en": "Demo language" },
  "normalizer": {
    "lowercase": true,
    "charMap": { "ʔ": "'" },
    "stripDiacritics": true,
    "preserve": ["é"]
  },
  "notationChars": "-=<>…~*",
  "boundaries": [" "],
  "costs": {
    "substitute": 1.5,
    "delete": 1,
    "insert": 0.8,
    "overrides": { " ": { "substitute": 0.1, "delete": 0.1, "insert": 0.1 } }
  },
  "rules": [
    { "category": "流音", "label": { "en": "Liquids" }, "rules": [["r", "l", 0.1]] },
    {
      "category": "詞尾",
      "label": { "en": "Word-final" },
      "position": "final",
      "rules": [
        ["n", "ng", 0.1],
        ["h", "", 0.1]
      ]
    }
  ],
  "morphology": {
    "prefixes": [{ "form": "mu", "gloss": { "zh-TW": "主事焦點", "en": "AF" } }],
    "suffixes": [{ "form": "an" }],
    "infixes": [{ "form": "in" }],
    "reduplication": [{ "pattern": "Ca" }],
    "alternations": [{ "underlying": "t", "surface": "d", "position": "final", "cost": 0.05 }]
  }
}
```

## 欄位

### `normalizer` 正規化

比對之前，查詢與詞庫都經過同一套正規化，依序：

1. Unicode NFC
2. `lowercase`（預設 true）：轉小寫
3. `charMap`：逐字元對應。**疊加在框架預設對應之上**（各種撇號 `’ ‘ ʼ ´` → `'`、`ǝ` → `ə`、全形與不斷行空白 → 空白）；
   設 `"useDefaultCharMap": false` 可以不要預設對應。值可以是多個字元（`"ŋ": "ng"`）或空字串（刪除）
4. `stripDiacritics`（預設 false）：去除附加符號；`preserve` 列出的字元例外（例如噶哈巫語的 `é` 是獨立的音位）
5. 連續空白壓成一個、去除頭尾空白

`charMap` 不要寫成連鎖（`a → b` 又 `b → c`）：正規化必須**冪等**，已正規化的詞再正規化一次不能改變。建置端與搜尋端、搜尋引擎與詞庫索引可能對同一個詞各正規化一次，不冪等時兩邊的寫法會對不上。對應是依序套用的，連鎖的結果取決於先後順序，很容易寫錯（單元測試 `normalize.test.js` 有反例）。構詞搜尋只在正規化後的查詢上以字元切片，不再對片段正規化。

### `notationChars` 體例符號

辭典體例用的符號（詞綴連字號、附著詞等號、中綴括號…），建立搜尋鍵時刪除，但顯示時保留原樣。
預設 `-=<>…~*`。所以 `sikis-`、`ha=ka`、`<in>` 分別可以用 `sikis`、`haka`、`in` 找到。

### `boundaries` 詞邊界

決定規則的「詞首」「詞尾」範圍，預設 `[" "]`。片語中空白前後也算詞尾／詞首，所以 `bintul a ≈ bintun a`。

### `costs` 基本編輯成本

| 欄位         | 預設 | 說明                                                                               |
| ------------ | ---- | ---------------------------------------------------------------------------------- |
| `substitute` | 1.5  | 替換一個字元（相同字元為 0）                                                       |
| `delete`     | 1.0  | 刪除查詢的字元（查詢多打了）                                                       |
| `insert`     | 0.8  | 補上候選的字元（查詢少打了）                                                       |
| `overrides`  | —    | 針對單一字元覆寫，例如讓空白的三種操作都只算 0.1，`baruzakbinayu ≈ baruzak binayu` |

插入比刪除便宜，是因為使用者常只記得詞的一部分。所以距離不對稱：`distance(a, b)` 與 `distance(b, a)` 可能不同。

### `rules` 語音對應規則

依分類分組的規則表。每組：

| 欄位          | 說明                                                                                         |
| ------------- | -------------------------------------------------------------------------------------------- |
| `category`    | 分類代號，也是預設顯示名稱。演算法實驗室可以整類開關                                         |
| `label`       | 各介面語系的分類名稱，例如 `{ "en": "Word-final" }`；只影響顯示                              |
| `description` | 說明（選填）                                                                                 |
| `position`    | 整組的位置限制：`any`（預設）、`initial`（詞首）、`final`（詞尾）                            |
| `rules`       | 規則列：`[來源, 目標, 權重]`，或物件 `{ source, target, weight, position?, bidirectional? }` |

規則的語意：

- **多字元對多字元**：`["aru", "aw", 0.1]`
- **一側可以是空字串**：`["r", "", 0.1]` 表示 r 脫落；兩側不能都空
- **預設雙向**：`r → l` 同時註冊 `l → r`；物件列可以設 `"bidirectional": false`
- **位置限制**對兩側都成立：`final` 表示來源片段在查詢的詞尾，**且**目標片段在候選的詞尾。構詞搜尋中，目標片段在詞素交界時（例如詞幹接後綴之前），查詢那一側不另外檢查（[bcdp.md](bcdp.md) 1.3）
- 權重必須非負（剪枝的正確性依賴這一點）；同一條規則重複出現時取最小權重
- 規則字串也會經過同一套正規化

### `morphology` 構詞（選填）

宣告這個語言的詞綴，搜尋就能雙向處理衍生詞：

- **自動拆解**（去詞綴）：查衍生詞，演算法找到詞根，也列出辭典已標註的派生詞。詞幹與詞綴本身都可以帶方言音變：`minudox` 得到 `daux-`（`minu-` ＋ `dox`，dox → daux 是 o → au）。
- 音變以**整個詞**計算：同一套方言規則套在「詞綴 · 詞根 · 詞綴」接起來的字串上，可以跨越詞素交界。`takitaw`（ta- ＋ kita ＋ -aw）的 a｜a 由規則 aa → a 處理，`tau'alawan`（tau- ＋ alaw ＋ -an）交界上的喉塞音由詞首規則 ' → ∅ 處理，都不必在詞綴清單中另列異體。
- **自動派生**（還原詞綴）：查詞根，找到詞庫與例句中演算法推定由它衍生的詞，包括中綴、重疊形式、方言變體，以及派生詞的派生詞。例如查 `baket` 得到 `binaket`（`b<in>aket`）。建置時由 BCDP 算好（自動派生圖，[bcdp.md](bcdp.md) 第 10 節）。

兩者都是演算法推定的，介面上標「自動拆解」「自動派生」；辭典標註的構詞關係（詞條家族、`<`）另外標「確定拆解」「確定派生」「確定同根」，不受這裡的規格影響。

| 欄位                              | 預設      | 說明                                                                                    |
| --------------------------------- | --------- | --------------------------------------------------------------------------------------- |
| `cost`                            | 0.3       | 每個構詞步驟的預設成本（個別詞綴、重疊、構詞音變可以用自己的 `cost` 覆寫）              |
| `minStem`                         | 3         | 詞根（詞庫詞）的最短長度（code point），太短的詞根容易巧合命中；見[步數預算](#步數預算) |
| `maxSteps`                        | 3         | 前綴、後綴各自最多幾個（見[步數預算](#步數預算)），整數 0–10                            |
| `lemmaSpread`                     | 0.6       | 自動拆解只保留成本在「最佳 ＋ lemmaSpread」之內的詞幹，控制候選數                       |
| `vowels`                          | `aeiouéə` | 元音字母，決定首輔音、中綴的位置與重疊模板                                              |
| `prefixes`、`suffixes`、`infixes` | —         | 詞綴清單，見[詞綴](#詞綴)                                                               |
| `reduplication`                   | —         | 重疊型式，見[重疊](#重疊)                                                               |
| `circumfixes`                     | —         | 環綴與包覆單位（幾個部分一起算一個步驟），見[環綴](#環綴)                               |
| `morphemes`、`constructions`      | —         | 構詞文法（取代上面五種清單），見[構詞文法](#構詞文法)                                   |
| `alternations`                    | —         | 構詞音變（只在詞素交界適用的規則），見[構詞音變](#構詞音變)                             |

已移除的欄位 `lemmaDistance`、`affixDistance`（音變改以整個詞計算），以及構詞音變的 `before`，出現時 `babizu check` 會報錯並說明原因。

每一筆詞綴、重疊、構詞音變都可以加：

| 欄位    | 說明                                                                       |
| ------- | -------------------------------------------------------------------------- |
| `gloss` | 顯示用的語法說明，字串或依語系的物件 `{ "zh-TW": "主事焦點", "en": "AF" }` |
| `cost`  | 這一步的成本，覆寫預設的 `cost`                                            |
| `ref`   | 出處，例如 `"Li & Tsuchida 2001, p. 15"`。只供維護者查證，不顯示           |
| `note`  | 附註，例如歸類的理由或限制。只供維護者查證，不顯示                         |

拼錯的欄位名稱（例如 `suffix`、`costs`）會被當成錯誤，而不是默默忽略。

演算法（BCDP）的正式定義、推導與正確性證明見 [bcdp.md](bcdp.md)。

## 編寫指南

### 方言規則

規則描述的是「同一個詞在兩個方言或兩套拼寫中，會系統性地怎麼不同」。寫之前先找平行的詞對，例如同一個詞在兩個方言的寫法，看差異是否反覆出現。

| 要描述的現象       | 寫法                            | 例子                                                     |
| ------------------ | ------------------------------- | -------------------------------------------------------- |
| 兩個音位互換       | 雙向規則                        | `["u", "o", 0.1]`：巴宰語 u、噶哈巫語 o                  |
| 一個音脫落         | 一側為空字串                    | `["r", "", 0.1]`：閃音 r 的脫落                          |
| 脫落造成元音變化   | 多字元規則                      | `["ar", "aa", 0.1]`：r 脫落後元音延長                    |
| 只在詞尾發生       | 整組 `"position": "final"`      | `["l", "n", 0.1]`：`bintul` ＝ `bintun`，但詞中的 l 不變 |
| 只在詞首發生       | 整組 `"position": "initial"`    |                                                          |
| 只有一個方向       | 物件列 `"bidirectional": false` | 拼寫系統把某個音寫成兩個字母，但反過來不成立             |
| 不同拼寫系統的寫法 | 另成一組，分類名稱標清楚        | `["dz", "d", 0.1]`                                       |

**權重怎麼定**：

- 方言間**系統性**的對應：0.1
- 常見但不規則的對應、拼寫系統之間的差異：0.2–0.3
- 一般替換 1.5、刪除 1.0、插入 0.8，所以一條規則的權重應該遠低於 1，否則等於沒有規則

網站的篩選面板有三段「模糊程度」：精確、標準、寬鬆，對應的距離門檻見 `src/search/engine.js` 的 `FUZZINESS`（門檻隨查詢長度放寬）。以門檻 0.3–0.5 來說，一個詞能容納三到五條 0.1 的規則。

**詞首、詞尾規則在詞素交界也適用**（[bcdp.md](bcdp.md) 1.3）：

- `babulay` 找得到 `babun`：詞尾的 l → n 在加了後綴 `-ay` 之後仍然存在。
- 元音開頭的詞素接在另一個詞素後面時寫出的喉塞音，是一條詞首規則 `["'", "", 0.1]`：它在詞首與每個詞素交界都適用，所以 `tau'alawan`、`kaxi'eder`、`ali~'ali` 都找得到，普通搜尋也把 `'alaw` 視為接近 `alaw`。
- 如果某個語言的詞尾音變在加後綴時會消失，就不要把它寫成詞尾規則。

**沒有位置限制的規則可以跨越詞素交界**：`["aa", "a", 0.1]` 讓 `takitaw`（ta- ＋ kita ＋ -aw）找得到 `kita`。有位置限制的規則只能碰到交界，不能跨越。

### 詞綴

`form` 寫成**搜尋鍵的形式**：不含連字號，經過同一套正規化（大小寫、`charMap`）。

- **每個異體各寫一筆**。巴宰語的主事焦點前綴有 `m-`、`me-`、`mi-`、`mu-`，依詞根的第一個元音而定；搜尋只需要「剝得掉」，不必知道條件，所以都列出來。文法寫法把它們寫在同一個詞素的 `forms` 裡（[構詞文法](#構詞文法)）。
- **主事與非主事形式都要列**，例如 `ma-` 與 `pa-`、`maxa-` 與 `paxa-`。
- **詞綴與詞根之間的音變不要列成異體**，寫成規則：插入的喉塞音（`kaxi'eder`、`pu-batu'-an`）是詞首規則 `' → ∅`，交界的元音合併（`maxa-apux` 寫作 `maxapux`）是 `aa → a`。這些規則對整個詞計算，在每個交界都適用。
- **中綴出現在前綴之中**（`m<in>u-baket` 寫作 `minubaket`）時，平面清單寫法把整段 `minu` 列為前綴：分析器的中綴只插在詞幹的首輔音之後，看不到前綴裡面。文法寫法寫成組合規則 `["AF", "PRF"]`，展開時自動插進前綴，說明也會顯示兩個詞素。
- **方言規則描述得到的差異不必列**：噶哈巫語 `mo-` 對巴宰語 `mu-`（u ↔ o 是 0.1）由規則處理，說明中標為「前綴」上的音變。規則描述不到的（中綴在前綴中）才列成異體。
- **單一字母的詞綴要謹慎**：`a-`、`i-`、`m-` 這類詞綴能剝的地方很多，雜訊（其他詞幹）會明顯增加。只收文法來源確實列出的。

`gloss` 取自文法來源的說明。沒有說明的就不填，介面只顯示形式。

### 重疊

重疊部分放在詞幹前面，由**詞幹**依模板產生。模板以 `vowels` 區分元音與輔音：

| `pattern` | 重疊部分                                    | 例子                            |
| --------- | ------------------------------------------- | ------------------------------- |
| `Ca`      | 首輔音（群）＋ a；元音開頭的詞幹只有 a      | `da~dius`、`la~luzuk`、`a~alep` |
| `CV`      | 首輔音＋第一個元音                          | `ki~kiliw`、`du~dusa`           |
| `CVV`     | 首輔音＋第一個元音，元音加長                | `dee~depex`、`kii~kita`         |
| `CVN`     | 首輔音＋第一個元音核（至少兩個元音）        | `ria~riak`、`tia~tianak`、`ziu~ziux` |
| `CVCV`    | 從頭到第二個元音核為止（兩音節、去韻尾）    | `kipu~kipud-i`、`luba~lubahing` |
| `CVCVC`   | CVCV 再加上其後連續的輔音（兩音節、含韻尾） | `maa-kudung~kudung`             |
| `full`    | 整個詞幹                                    | `saw~saw`                       |

模板的細節：

- **首輔音**是第一個元音之前的所有字元，可以是空的，也可以是輔音群。
- **元音核**是連續的元音字母，`aa`、`iu` 都算一個。所以 `ziux` 只有一個元音核，CVCV 不適用，CVN 重疊整個元音核（`ziu~ziux`）；如果這個語言的元音連續其實分屬兩個音節，目前的模板描述不到（[bcdp.md](bcdp.md) 第 15 節的已知限制）。
- **CVN 與 CV 是同一種重疊**，只是詞根的第一個元音核有兩個元音時整個重疊（riak → ria~riak，不是 ri~riak）。元音核只有一個元音時 CVN 不適用（那就是 CV），所以兩者可以並列而不重複。巴宰語的設定檔也為 CVN 加上與 CV 相同的組合規則（UVL.PROG.CVN 等：`ria~riak-an`）。
- 不在 `vowels` 中的字元都算輔音，包括滑音 `y`、`w` 與喉塞音 `'`：`CVCV` 套在 `zizay` 上得到 `ziza`，韻尾的 y 去掉了。
- **模板只看詞幹，不看後綴**：`kipu~kipud-i` 的重疊部分由 `kipud` 產生。
- **重疊部分複製查詢的形式**：噶哈巫語 `maa-tono~tono` 的重疊部分跟著噶哈巫語的元音，詞幹 `tono` 再以方言規則對應到詞根。
- 同一種重疊語意在不同方言用不同模板時，兩種都列（巴宰語 CVCV、噶哈巫語 CVCVC）。
- 沒有單獨詞根的詞彙性重疊（例如只以重疊形式出現的名詞）不要當成構詞：它們本身就是詞庫中的詞。

### 環綴

`circumfixes` 描述一起出現的幾個部分，合起來算**一個**構詞步驟。一般的形式是**包覆單位** (L, op, R)：緊貼詞根的前綴 `prefix`、詞根上的中綴 `infix` 或重疊 `reduplication`、緊貼詞根的後綴 `suffix`。

```json
{ "prefix": "ta", "suffix": "aw", "gloss": { "zh-TW": "勸說・受事焦點", "en": "HORT.UVP" } }
{ "infix": "in", "suffix": "an" }
{ "reduplication": "Ca", "suffix": "ay" }
{ "prefix": "m", "infix": "a", "suffix": "ay", "gloss": { "zh-TW": "主事焦點・非實現", "en": "AV.IRR" } }
{ "prefix": "ma", "suffix": "ay", "stemInitial": "V", "gloss": { "zh-TW": "主事焦點・非實現", "en": "AV.IRR" } }
```

- 至少要有兩個部分；`infix` 與 `reduplication` 不能同時出現。
- `prefix` ＋ `infix`（m<a>-）：只有輔音的前綴加中綴，中綴落在詞根的首輔音之後（`m<a>-baket` 是 mbaaket，`m<a>-usa` 是 mausa），在詞根上還原（[morph-grammar.md](morph-grammar.md) 2.2）。
- `stemInitial: "V"`：詞根必須以元音開頭，只用於前綴式（可以沒有後綴）。它是上一項在元音開頭的詞根上的串接形式（ma ＋ usa），規則可以跨越它的交界（usa｜ay → usay 的元音合併）。文法寫法會自動產生這一項，不必手寫。
- **環綴緊貼詞根**：前綴式的左邊是最內層的前綴，後綴是最內層的後綴；其他詞綴只能加在外面：主事焦點前綴可以加在重疊式環綴 `Ca-…-ay` 的外面，但 `ta-…-aw` 的兩側之間不能再夾別的前綴。
- **為什麼需要**：只列前綴 `ta-` 與後綴 `-aw` 時，`ta-kita-aw` 要付兩個步驟的成本，會排在只用一個詞綴、音變較多的錯誤詞根之後。語法描述為一個構式（例如焦點、語氣表中的一格）的，就寫成環綴。
- 環綴的兩側不必另外列在 `prefixes`、`suffixes` 中；列了也沒關係，單獨出現時照樣可以分析。
- 主事焦點前綴有幾個異體時（`m-`、`mu-`、`mi-`、`me-`），平面清單寫法每個異體各寫一筆；文法寫法寫一條組合規則，展開時每個異體各一項。

### 構詞文法

平面清單的某些詞綴其實是幾個詞素的組合（minu ＝ m<in>u、ma-…-ay ＝ m<a>-…-ay），或一個詞素有幾個形式（m-、mu-、mi-、me-）。這時可以改用文法寫法：`morphemes` 列出最小詞素，`constructions` 列出固定的組合。文法在載入時展開成平面清單，搜尋與原本完全相同；差別在說明會顯示詞素與構式，也不必手動想出每個前綴與中綴的組合。定義、編譯原理與證明見 [morph-grammar.md](morph-grammar.md)。

```json
"morphology": {
  "cost": 0.2,
  "morphemes": [
    { "id": "AF", "type": "prefix", "forms": ["m", "mu", "mi", "me"], "gloss": { "zh-TW": "主事焦點", "en": "AF" } },
    { "id": "AF.m", "type": "prefix", "form": "m", "free": false, "gloss": { "zh-TW": "主事焦點", "en": "AF" } },
    { "id": "PROG", "type": "infix", "form": "a", "gloss": { "zh-TW": "非完成貌", "en": "PROG" } },
    { "id": "PRF", "type": "infix", "form": "in", "gloss": { "zh-TW": "完成貌", "en": "PFV" } },
    { "id": "IRR", "type": "suffix", "form": "ay", "gloss": { "zh-TW": "非實現", "en": "IRR" } },
    { "id": "HORT", "type": "prefix", "form": "ta", "free": false },
    { "id": "HORT.aw", "type": "suffix", "form": "aw", "free": false }
  ],
  "constructions": [
    { "id": "AF.PFV", "sequence": ["AF", "PRF"], "gloss": { "zh-TW": "主事焦點・完成", "en": "AV.PFV" } },
    { "id": "AF.IRR", "sequence": ["AF.m", "PROG", "IRR"], "gloss": { "zh-TW": "主事焦點・非實現", "en": "AV.IRR" } },
    { "id": "HORT.UVP", "sequence": ["HORT", "HORT.aw"], "gloss": { "zh-TW": "勸說・受事焦點", "en": "HORT.UVP" } }
  ]
}
```

AF.PFV 的四個形式都有證據（m<in>-、m<in>u-、m<in>i-、m<in>e-），所以引用 AF；AF.IRR 只有 m<a>-…-ay，所以引用只有 m 的 AF.m（見[編寫技巧](#編寫技巧依-bcdp-的運作原理)）。

文法寫法與平面清單寫法（`prefixes`…`circumfixes`）二選一；`cost`、`minStem`、`maxSteps`、`lemmaSpread`、`vowels`、`alternations` 兩種共用。

**怎麼寫**：

1. **一個詞素的幾個形式寫在 `forms`**。不寫分布條件：資料中常有例外（噶哈巫語 `mu-aping`），搜尋不檢查，用了哪一個由查詢本身決定。分布寫在 `note` 裡供查證。
2. **語法描述為一個構式的組合寫成組合規則**（焦點・時貌表中的一格），`sequence` 依**推導順序**：先加上去的在前。`["AF", "PRF"]` 是 m<in>u-（minubaket），`["PRF", "AF"]` 是 mu- ＋ b<in>aket（mubinaket）。
3. **只在構式裡出現的詞素**設 `free: false`：勸說的 ta- 只與 -i、-aw 一起出現，單獨的 ta- 是另一個詞素（主事者）；-aw 只在 ta-…-aw 中出現。
4. 自由詞素單獨出現時的成本是詞素的 `cost`；組合規則整個算一個步驟，成本是組合規則的 `cost`。

**展開成什麼**：

| `sequence`（形式） | 展開 |
|---|---|
| AF（mu）＋ PRF（in） | 前綴 minu（中綴插在前綴的首輔音之後） |
| AF（m）＋ PRF（in） | 包覆單位 (m, <in>, ∅)，加上元音開頭詞根的前綴 min |
| AF.m（m）＋ PROG（a）＋ IRR（ay） | 包覆單位 (m, <a>, ay)，加上元音開頭詞根的 ma-…-ay |
| AF（mu）＋ PROG（a）＋ IRR（ay） | 前綴式環綴 mau-…-ay（引用 AF 時才會有；巴宰語的設定檔不要它） |
| RED.CV ＋ LF（an） | 重疊式環綴 CV~…-an |
| HORT（ta）＋ HORT.aw（aw） | 前綴式環綴 ta-…-aw |

只有一側的結果（minu、kina）是一般的前綴，可以與其他前綴串接（kina- ＋ tu- ＋ babaw）。

**成對的詞綴一定寫成組合規則**。語法上成對出現的詞綴（巴宰語非實現貌的 ‹a›…-ay）若分開寫，BCDP 會把它們當成兩個獨立的步驟，
分析也會錯：

- pausunguday（將要造橋）＝ p‹a›u-sungud-ay：‹a› 插在前綴 pu 的首輔音之後，與 -ay 一起表示非實現。
- 只有自由的 PROG、IRR 時，最好的分析是 pusungut ＋ ‹a› ＋ -ay（兩步 0.45），詞根是 pusungut，說明把 ‹a›、-ay 拆開。
- 加上組合規則 `{ "id": "PU.IRR", "sequence": ["pre.pu", "PROG", "IRR"] }` 之後，編譯成一個環綴 pau-…-ay，
  分析是 sungut ＋ p‹a›u-…-ay（一步 0.2 ＋ 詞根末 t → d 0.05），說明列出 pu-、‹a›、-ay 三個詞素。

巴宰語的設定檔為語料中有 C‹a›V-…-ay 形式的前綴各寫一條（PU.IRR、PI.IRR、CAUS.IRR、KA.IRR：pausunguday、paizauxay、paakizihay、kaakanay），
沒有證據的前綴不寫（理由見[編寫技巧](#編寫技巧依-bcdp-的運作原理)第 1 項）。加上之後，評估工具（minubizu 的 `eval-segmentation.mjs`、`eval-morphology-search.mjs`）的數字不變，只有用到這些構式的詞改成正確的分析。

**規格錯誤**：

- 重疊不是推導的第一步；
- 一條規則有兩個落在詞根上的中綴或重疊；
- 展開後超過 5,000 項。

`babizu check` 會指出是哪一條規則、哪一種形式選擇。

**檢查展開結果**：

```js
import { expandGrammar } from 'babizu/fuzzy'
const flat = expandGrammar(profile.morphology)
console.table(flat.prefixes.filter((e) => e.parts.length > 1))
console.table(flat.circumfixes)
```

**注意**：

- **規格中的順序有意義**：成本相同時，說明選步驟少的，再選自由詞素，最後依規格順序。
- **組合規則的每一種形式選擇都會展開**，不論資料中有沒有出現：只要構式實際用到的形式，另寫一個 `free: false` 的詞素（下一節第 1 項）。

### 編寫技巧：依 BCDP 的運作原理

搜尋時，設定檔的每一項都是一個「到處都要試一次」的假設。多一個假設，搜尋就多一點工作；假設錯了，還會在同分或成本相近時贏過正確的分析。所以設定檔要**寫得剛好**：語言中有的都寫進去，沒有證據的不要寫。這一節說明每一項在 BCDP 中做什麼（演算法見 [bcdp.md](bcdp.md)），以及據此整理出的技巧。

**每一項在搜尋時做什麼**：

| 設定檔的項目 | BCDP 中的工作 | 代價 |
|---|---|---|
| 前綴、後綴 | 詞綴 trie 上的節點；前綴、後綴各一層一層走，至多 `maxSteps` 層（bcdp.md 第 5 節） | 詞綴本身很便宜；但越短、越常見的詞綴，讓越多查詢位置成為詞幹的起點 |
| 單獨的中綴、重疊 | 在每個詞幹起點試著拿掉，成立的成為一個還原變體，多一個通道（第 6 節） | 每個成立的變體多走一次詞圖（起點固定，剪枝很強） |
| 前綴式環綴 | 後綴相同的合併成一個通道（第 7 節） | 每多一種後綴，最多多一個通道 |
| 要求詞根元音開頭的環綴（`stemInitial`） | 併進後綴相同的通道，只換元音開頭的詞的起點 | 幾乎沒有 |
| 外側有前綴的包覆單位（m<a>-） | 還原變體，起點在「前綴鏈 · 前綴」之後 | 同單獨的中綴 |
| 組合規則 | 每一種同位詞素選擇展開成上面的一項 | 形式選擇越多，項目越多 |
| `free: false` 的詞素 | 不展開成單獨的一項 | 省掉一個到處都要試的假設 |

**技巧**：

1. **組合規則只展開有證據的形式**。組合規則引用一個詞素時，它的每一個形式都會展開。構式只用其中幾個時，另寫一個 `free: false` 的詞素，只列那幾個形式，組合規則引用它。
   - 巴宰語：主事焦點的非完成貌只有 m<a>-（元音開頭的詞根），所以 AF.PROG、AF.IRR 引用只有 m 的 AF.m。原本引用 AF 時會展開出 mau-、mai-、mae-：資料中沒有這些形式，mausay 的第一名卻因此變成 mau- ＋ say。
2. **同一個構式在不同詞根上形式不同時，寫成兩條規則**，各引用各的形式。巴宰語的主事焦點・非實現：元音開頭的詞根是 m<a>-…-ay（AF.IRR，引用 AF.m），其他的是 mu-、mi-、me-…-ay（AF.IRR2，引用只有這三個形式的 AF.C）。m-…-ay 在資料中沒有出現，卻會把 maudalay 拆成 m- ＋ audal ＋ -ay。
3. **只在構式中出現的詞素設 `free: false`**。自由的詞綴在每個交界都會被試。巴宰語的 -aw 只在 ta-…-aw 中出現；它原本是自由的後綴，於是 masuhaw、mataw 被拆成 masu-aw、mata-aw。
4. **不要為了「以防萬一」加詞綴**。從資料學出的單一字母詞綴、重疊的殘片，讓召回多一點，雜訊與耗時卻明顯增加。單一字母的詞綴（a-、i-、m-）代價最高，因為能剝的位置最多；文法來源確實列出、資料也用得到時才收。
5. **交界現象寫成規則，不寫成異體**（見[方言規則](#方言規則)與[構詞音變](#構詞音變)）。喉塞音增生、元音合併一條規則就涵蓋所有詞綴；列成異體則每個都要多試一次。
6. **後綴的種類決定通道數**。前綴式環綴依後綴合併成通道，所以同一個語法意義盡量用同一個後綴形式；真的有異體（-en、-un）時照實列出。
7. **規格的順序決定同分時的說明**：步驟少的優先，再依規格順序，自由詞素在組合規則之前。常用的形式放前面。
8. **`maxSteps`、`lemmaSpread` 用預設**。巴宰語 2,141 組詞對中，用到三個前綴或三個後綴的只有 12 組；降低 `maxSteps` 省下的工作很少，卻會漏掉這些詞。

**怎麼檢查**：

- **展開結果**：`expandGrammar`（上一節）。每一項都應該能在文法來源或資料中找到例子。
- **每一項用了幾次**：拿資料中標註的「衍生詞 < 詞根」，查每個衍生詞，看標註的詞根的分析用到哪些項目，以及排第一的錯誤詞根用到哪些項目：

  ```js
  import { buildSearchIndex, SearchEngine } from 'babizu/search'
  const engine = new SearchEngine(buildSearchIndex({ items, groups, sourceIds, profile, varieties }))
  const unit = (s) => (s.parts?.length ? s.parts.map((p) => `${p.id}=${p.form}`).join('+') : `${s.type}:${s.form}`)
  for (const { derived, root } of pairs) {
    const hits = engine.morphSearch.search(engine.text.searchKey(derived), { maxDistance: 1 })
    const right = hits.find((h) => h.term === root) // 正確的分析用到的：hits 裡這一筆的 steps
    const wrong = hits[0]?.term !== root ? hits[0] : null // 排第一的錯誤分析用到的
    // 依 unit(step) 分別計數
  }
  ```

  從來沒有用在正確分析、卻常出現在排第一的錯誤分析的項目，就是要限縮或設 `free: false` 的對象。
  - 例外：錯誤的第一名若是詞庫中另一個本身就是衍生詞的詞，而且成本與正確的分析相同，例如 maatabilih 分析成 <a> ＋ matabilih，而不是 maa- ＋ tabilih，那不是設定檔的問題，而是兩種分析深度同分。
- **工作量**：計數，而不是計時。計數與機器負載無關，比較兩份設定檔時差 1% 也看得出來：

  ```js
  const ms = engine.morphSearch
  const stats = { visitedNodes: 0, prunedNodes: 0, computedRows: 0 }
  let channels = 0
  for (const q of queries) {
    const p = ms.seed(ms.prepare(engine.text.searchKey(q), 1))
    if (!p) continue
    channels += p.channels.length
    engine.index.searchChannels(p.channels, stats)
  }
  // channels：通道數；stats.computedRows：DP 算了幾列（詞圖走訪的主要工作）
  ```

- **效果**：改動前後都量找詞根的召回與第 1 名比例，以及拆解正確率。規格若是由這批詞對調整的，要另外保留一部分詞對只用來評估（見上面的[怎麼檢查](#怎麼檢查)）。

**巴宰語的例子**：上面第 1–3 項的改動，前後比較如下。「平面清單」是改寫成文法之前的設定檔。

| | 文法，未整理 | 整理後 | 平面清單 |
|---|---|---|---|
| 展開後的前綴／後綴／包覆單位 | 69／7／27 | 66／6／23 | 65／7／15 |
| 每個查詢 DP 算的列（821 個查詢） | 5,802 | 5,687 | 5,622 |
| 找詞根第 1 名：S1／S2／S3／S3b | 81.1／67.6／71.2／72.7% | 81.4／68.2／71.8／73.7% | 81.1／67.6／—／72.7% |
| 其他詞幹（S1，每個查詢） | 6.31 | 6.08 | — |
| mausay 的第一名 | say（mau- ＋ say） | usa（m<a>-…-ay） | usa（ma-…-ay，標註錯） |

- S1 是查詢衍生詞本身，S2 是套上一條方言規則，S3 是 S2 而且衍生詞不在詞庫中，S3b 是音變落在詞綴或跨越交界的；每 2 組取 1 組。
- 召回沒有變，拆解正確率（潘德興詞彙表 179 筆）都是 53.1%。

### 構詞音變

`alternations` 描述**由構詞引起**、只在詞素交界發生的音變：底層的 `underlying` 在交界旁寫成 `surface`。它就是一條只在交界適用的規則（source ＝ `surface`，target ＝ `underlying`），與方言規則在同一個 DP 中計算。

```json
{ "underlying": "t", "surface": "d", "position": "final", "cost": 0.05 }
```

巴宰語詞根末的濁塞音在詞尾清化，只在元音開頭的後綴前出現：`alep` ＋ `-i` → `alebi`，`bitut` ＋ `-un` → `bitudun`。

- `position` 說明 `underlying` 在交界的哪一側：`final`（預設，詞素結尾、交界之前）、`initial`（詞素開頭、交界之後）、`any`（任一側）。
- 交界上的增生也是構詞音變：u 結尾的詞素接元音開頭的後綴時插入 w（`apu'apu-w-an`），寫成 `{ "underlying": "u", "surface": "uw", "position": "final", "cost": 0.1 }`。
- 沒有「只在某些後綴前」的條件：交界就是條件。需要區分時，通常表示那其實是詞綴的異體，列在詞綴清單中。
- **成本要低於對應的方言規則**。方言規則「濁化」t ↔ d 是 0.1 時，把構詞音變設為 0.05：兩種解釋都成立時，說明會顯示為構詞音變，而不是方言差異。
- 構詞音變不佔用步數預算，也不算「至少一個構詞步驟」：它是音變，不是步驟。
- `underlying`、`surface` 可以是多個字元，但參考用的 WFST 後端不支援構詞音變，比較時先去掉。

### 交界語意

- **構詞不跨越空白**：詞綴、中綴、重疊部分都不能含空白，詞素交界也不能在空白旁（`mu daux` 是兩個詞）。片語中每個詞的構詞交給搜尋引擎的逐詞搜尋。
- **詞幹可以含空白**：詞庫中含空白的詞條（複合詞）可以當作詞幹。
- **詞首、詞尾規則在詞素交界也適用**，沒有位置限制的規則可以**跨越**交界（見[方言規則](#方言規則)）。
- **構詞音變只在交界適用**（見[構詞音變](#構詞音變)）。
- 中綴、重疊的交界固定在查詢的位置上，規則不能跨越。

### 步數預算

- 前綴至多 `maxSteps` 個，後綴也至多 `maxSteps` 個，**各自計算**：`maxSteps` 為 3 時，三個前綴加兩個後綴也可以。
- 另外至多一個**包覆單位**：中綴、重疊、環綴，或「前綴 ＋ 中綴（＋ 後綴）」的組合（m<a>-…-ay）。中綴之後再重疊這類組合目前不支援。
- 每一步都要付成本，所以步數多的分析自然排在後面；`maxSteps` 只是防止列舉爆量，一般不需要改。
- `minStem` 限制的是詞根（詞庫詞）的長度。查詢至少要有 `minStem` ＋ 1 個字元才做構詞搜尋，詞幹在查詢中的寫法可以比 `minStem` 短，只要整個分析的成本在上限內。
- 沒有「詞幹部分的音變上限」：整個分析只受總成本上限與 `lemmaSpread` 限制。

### 怎麼檢查

1. **格式**：`babizu check` 檢查整個設定檔。構詞規格的錯誤會指出欄位，例如 `morphology.reduplication[0].pattern 必須是 Ca、CV、CVV、CVCV、CVCVC、full 之一`。
2. **單一個詞**：到演算法實驗室（`/lab`）輸入兩個詞，逐格檢查編輯距離的計算，確認規則照預期生效。
3. **列舉式分析**：

   ```js
   import { createAnalyzer } from 'babizu/fuzzy'
   const { analyze, generate } = createAnalyzer(profile.morphology)
   analyze('binaket') // → [{ stem: 'baket', steps: [{ type: 'infix', form: 'in', … }], cost: 0.3 }, …]
   generate('baket', [{ type: 'infix', form: 'in' }]) // → 'binaket'
   ```

4. **整體效果**：如果資料中有標註的「衍生詞 < 詞根」，拿它們評估召回、第 1 名的比例與「其他詞幹數」（雜訊）。規格若是從這批詞對學出的，**一定要保留一部分詞對不用來學**，只拿它們評估，否則數字會偏樂觀。pazeh-kaxabu 的做法見其私有 repo 的評估工具與研究紀錄。

### 常見誤區

- **把學出的詞綴全部收進來**。從資料自動學出的清單常有單一字母的「詞綴」與重疊的殘片（例如把 `ta-bura~buray` 的 `tabura` 當成前綴）；它們讓召回多一點，雜訊與耗時卻明顯增加。以文法來源為主。
- **替每個交界現象列詞綴異體**：喉塞音、元音合併寫成規則，一條就涵蓋所有詞綴。只有規則描述不到的（中綴在前綴中）才列異體，或改用[構詞文法](#構詞文法)。
- **在組合規則裡寫同位詞素的分布條件**：文法沒有條件。資料中的例外會讓條件變成錯誤，而且量測顯示條件從來沒有決定過分析（[morph-grammar.md](morph-grammar.md) 第 6 節）。
- **構詞音變的成本不低於方言規則**，說明就永遠顯示成方言差異。
- **期待模板看到後綴**，或期待右分支重疊（重疊詞幹的後兩個音節，而不是前兩個）：目前都不支援。
- **把只在詞尾發生、但加後綴就消失的音變寫成詞尾規則**：詞首、詞尾規則在詞素交界也適用。

## 驗證

`babizu check` 會檢查結構（`format`、`version`、型別、構詞規格的每個欄位）；規則內容（權重非負、兩側不同時為空）在建立規則集時檢查。

程式中也可以直接使用：

```js
import { createMetricFromProfile, validateProfile } from 'babizu/fuzzy'

validateProfile(profile) // → 錯誤訊息陣列
const metric = createMetricFromProfile(profile)
metric.distance('ralan', 'lalan') // 0.1
metric.explain('ralan', 'lalan') // 完整 DP 表與對齊路徑
```

搜尋索引的格式與大小不因構詞規格而改變（構詞比對都在查詢時進行）；改了規格只要重新建置網站。精確模式不做構詞比對。
